# GitHubble Mirror Manager — этап I

Основная ветка разработки: `feat/mirror-manager` на базе `feat/unified-agent-stage3`. PR #52.

## Текущие возможности

- Нативный экран из карточки репозитория и настроек GitHub, выбор другого подключённого аккаунта.
- Раздельные токены из защищённого GitHubAccountStore без переключения активного аккаунта и без их отправки в GitHub Actions.
- Создание **GitHub Fork** с `default_branch_only=false`: сервер GitHub переносит историю и все ветки, исходники и Git-архивы на телефон не загружаются.
- Возможность задать имя, предварительно проверить наличие назначения, запрет на перезапись существующего репозитория.
- Журнал операций, проверка Git heads/tags по SHA, состояния RUNNING / VERIFIED / FAILED / DIVERGED.
- Параллельная работа нескольких подключённых аккаунтов без смешивания сессий.
- Android и JVM-тесты с отдельным workflow CI.

## Важное разграничение

**Fork не является полностью независимым Git mirror.** Он отображается на целевом аккаунте как fork, связан с upstream; GitHub управляет копированием и ограничениями forks. На этом этапе перенос работает только для публичного источника, при достаточных GitHub App правах. Для некоторых установок GitHub App нужно разрешение на все репозитории источника и назначения.

Скелет независимого mirror runner (MirrorWorkflow / dispatch / state tracker) сохранён для следующего этапа, но **не запускается пользовательским интерфейсом**. Причина: встроенный `GITHUB_TOKEN` GitHub Actions не имеет `Workflows: write` и не способен надёжно зеркалировать ветки с файлами `.github/workflows`. Нельзя создавать destination и обещать полный перенос с заведомо недостаточными правами.

## Следующие этапы

1. Защищённый short-lived credential broker для независимого `git push --mirror`, поддержка приватных репозиториев и копирования Git LFS.
2. Прозрачная повторная синхронизация с явным подтверждением destructive force/prune, конфликтами и расписанием.
3. Отдельный перенос Issues/PR/Releases и вложений (это не входит в Git-объекты). GitHub Secrets не экспортировать.

Никакие реальные пользовательские репозитории между аккаунтами в рамках разработки не переносились.
