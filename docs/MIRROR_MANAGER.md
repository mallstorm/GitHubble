# GitHubble Mirror Manager — этап I

Исходная ветка: feat/unified-agent-stage3. Новая функциональная ветка: feat/mirror-manager.

## Что реализовано
- Вход из карточки репозитория и из настроек GitHub.
- Выбор другого подключённого аккаунта и названия **нового** целевого репозитория.
- Два режима: разовая копия; управляемое зеркало с ручным повторным обновлением.
- Отдельные GitHub API-сессии для двух аккаунтов без переключения активного аккаунта. Токены берутся из SecureStore по ID и не передаются в GitHub Actions.
- Проверка личности обеих сессий через /user, публичности источника и отсутствия назначения. Уже существующий сторонний репозиторий при первом запуске никогда не перезаписывается.
- Создание пустого назначения, установка той же default branch, временный workflow_dispatch для hosted runner GitHub Actions.
- Runner копирует Git-историю, ветки, теги и Git LFS. Мобильный клиент отправляет только операции через REST API, не скачивает ZIP/git tree.
- Записи операций сохраняются в SharedPreferences; поддерживается повторная проверка Actions и сравнение всех доступных heads/tags по SHA.
- Повторная синхронизация требует отдельного подтверждения и может выполнять force/prune только для ранее созданного управляемого зеркала.
- Отказ от повторного автоматического запуска неизвестной мутации, сопоставление запуска по request_id.

## Ограничения и требования
- Этап I работает **только с публичным исходным репозиторием**; приватный источник блокируется до создания безопасной инфраструктуры. Не передавайте OAuth токены через workflow_dispatch или GitHub issues.
- Разовый перенос Git refs не равен копии Issues, Pull Requests, Discussions, Releases-assetов, веточных настроек, секретов и политики репозитория. Это отдельные этапы.
- Поддерживаются refs/heads/* и refs/tags/*. Внутренние служебные refs GitHub (например refs/pull/*) не зеркалируются.
- Целевой GITHUB_TOKEN ограничен репозиторием, в котором запущен workflow. Нужны contents:write и доступ Actions. Текущие правила GitHub для изменений .github/workflows могут требовать дополнительных прав Workflows:write. Если GitHub отклоняет замену workflow, план перейдёт в ошибку: нельзя заявлять успех.
- При защищённых ветках/правилах repository rulesets GitHub может отклонить push --force. Смена прав без согласия пользователя не выполняется.
- При возникновении ошибки после создания назначения оно остаётся пользователю; приложение не удаляет репозитории автоматически.
- Для начального переноса создаётся новый репозиторий, а не копируется весь архив на телефон.
- Постоянное облачное зеркало по webhook/расписанию, перенос приватного кода через защищённый сервис, Releases/Issues/PR и восстановление/отмена длительных операций — отдельный следующий этап.

## Действия пользователя
1. Открыть репозиторий на исходном аккаунте и выбрать «Mirror Manager».
2. Выбрать целевой аккаунт, задать имя, выбрать разовую копию или управляемое зеркало.
3. Подтвердить создание (только новый target).
4. Проверить статус cloud-run в списке зеркал, при необходимости открыть журнал Actions.
5. При повторной синхронизации отдельно подтвердить возможную перезапись/удаление target refs.

## Безопасность
- Никакие исходные OAuth-токены не записываются в план или workflow.
- Workflow принимает только публичное имя source (owner/repo) и неприватный request_id.
- Для записи destination runner использует только ephemeral GITHUB_TOKEN конкретного target.
- Операции на аккаунтах не смешиваются из-за глобального выбора «активного» пользователя.
- До полноценного продакшен-включения необходимо провести end-to-end проверку на двух тестовых GitHub-аккаунтах и проверить ограничения .github/workflows / LFS.
