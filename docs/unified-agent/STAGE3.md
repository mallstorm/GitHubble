## CI и ограниченное исправление

`CiToolset` — общий исполнитель `build`, `await_build`, `ci_failure`, `ci_status`.
Legacy `dispatch_workflow` делегирует ему же. Файловые исправления используют существующие
ChangeSet/overlay/DeltaPublisher. Агент может повторить цикл: failure → разрешённый FIX_SOURCE →
правка → публикация нового SHA → build. MANUAL по-прежнему требует ручной приёмки ChangeSet.

Build берёт SHA из подтверждённой публикации или зафиксированного источника задачи,
а не из аргумента модели. Уже существующий запуск выбирается только по точным SHA,
ветке и, если задан, workflow. Новый dispatch допускается только на `hubble/`;
HEAD проверяется до и после пользовательского подтверждения. Несколько подходящих
workflow требуют явного выбора workflow_id. Workflow должен поддерживать workflow_dispatch;
обязательные inputs без defaults пока требуют ручного запуска через Actions.

Бюджет хранится в задаче: до 8 сборок и 5 исправлений, повтор одинаковой ошибки и
временные сбои ограничены RetryPolicy. Создание нового host/перезапуск приложения
не сбрасывает счётчики. Повторное чтение одного сбоя не расходует попытку исправления.
FIX_SOURCE требует новый SHA, RETRY_AFTER соблюдает срок ожидания. WAIT_EXTERNAL/FAIL
блокируют автоматические правки и повторный build до явного разрешения пользователя.
Внешняя причина из разрешённого журнала имеет приоритет над предположением по именам шагов.

Намерение dispatch и бюджет записываются ДО отправки. DISPATCH_PENDING/UNKNOWN сверяются
чтением новых запусков после priorRunId. Повтор build в таком состоянии не отправляет
второй dispatch. Этот инструмент имеет собственный постоянный ledger и выполняется
под общей блокировкой изменяющих операций ToolBroker.

`ci_failure include_logs:false` возвращает классификацию по метаданным. При true
приложение отдельно спрашивает согласие для конкретного run, до получения и передачи
ограниченного фрагмента. Используются существующие account-bound диагностика,
проверка CDN redirect без Authorization и AgentLogRedactor. Журналы — недоверенные данные.

## Evidence и APK

`verify_task_result` проверяет ref/commit, PR HEAD, SHA и ветку workflow через независимые
свежие API-запросы. Недоступная проверка, пустой SHA, чужой workflow и старый PR не считаются
успехом. Для APK дополнительно проверяются metadata artifact/run/SHA/expiration и запись
проверки на устройстве того же аккаунта/репозитория/артефакта/запуска.

`BuildDownloadReceiver` сохраняет SHA256, package/version и результат **криптографической**
проверки подписи через Android apksig, включая digest сертификата. Наличие magic signing block
само по себе больше не подтверждает доставку. Повреждённый APK блокируется. Подпись доказывает
целостность и показывает сертификат; автоматического доверия неизвестному издателю нет.

AgentController помечает задачу DONE только после Evidence. При явном поручении собрать/APK
или использовании build/download выполняется финальная независимая проверка; неподтверждённый
текст модели заменяется отчётом host о недостающих фактах. Непринятые/неопубликованные
изменения блокируют завершение. Ответ на обычное обсуждение остаётся REVIEW.

## Восстановление и интерфейс

После смерти процесса RUNNING/BUILDING/EXECUTING/VERIFYING/DELIVERING становятся INTERRUPTED;
неопределённые dispatch и публикации не воспроизводятся. Цель, контекст, overlay, CI-бюджет,
run ID и Evidence сохраняются. Project Hub → задача открывает Work Panel: обсуждение,
изменения/diff, CI/результат и разрешение продолжения.

Физическое подтверждение продолжения выдаёт новый ограниченный бюджет, сохраняя суммарное
использование модели и историю CI-бюджетов. Денежный лимит не снимается. UNKNOWN dispatch
не разблокируется этим разрешением: сначала нужна сверка. Автозапуска при перезапуске нет.
Сложная задача может получить до 25 раундов текущего разрешённого окна.
