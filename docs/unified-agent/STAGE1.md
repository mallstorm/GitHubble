# Unified Agent Engine 2.0 — этап I

База: `1.0.0-rc4.2.32`, versionCode `79`, commit
`3e5097fb7b4822ca1e08b09e8fac726b83380507`.
Основание: предложенная пользователем редакция ТЗ; подтверждение окончательной редакции Claude не заявляется.
Ветка: `feat/unified-agent-stage1`. В `main` изменения попадают только после приёмки PR.
Этапы II и III принимаются отдельными PR; этот этап не выпускает production APK.

## Данные и миграция

`ProjectRegistry` хранит постоянные проекты, `TaskRepository` — задачи с независимыми
ID, обсуждениями, состоянием, веткой, бюджетом и журналом инструментальных результатов.
`TaskSession` фиксирует аккаунт, проект и задачу на время исполнения.

Метаданные сохраняются атомарными account-scoped снимками в
`githubble_unified_agent_v2`. Перед нормализацией старых данных сохраняется неизменяемая
резервная копия метаданных соответствующего аккаунта. Миграция повторяема: ID проектов
детерминированы, ID старых обсуждений становятся ID задач. Совпадающий Workspace
объединяется; репозиторий объединяется только при однозначном сопоставлении.
Разные Workspace одного репозитория не сливаются. Повреждённые метаданные вызывают
явную ошибку, а не перезаписываются пустой базой.

Обсуждения и их архивы остаются в `AgentConversationStore`, исходники, SAF и checkpoint
остаются на исходных путях. `AgentProjectStore` служит адаптером старых UI-функций к
новому реестру и продолжает сохранять совместимые старые привязки. Удаление задачи
не удаляет проект и репозиторий. Удаление локального Workspace снимает все его привязки,
сохраняя проект и GitHub. Новый обычный диалог остаётся без проекта; новая задача
получает новый ID даже при наличии пустого черновика.

Для новых проектов область памяти привязана к Project ID; мигрированные проекты с
Workspace сохраняют прежнюю область памяти, чтобы не потерять сохранённые решения.
Незавершённый RUNNING после потери процесса становится INTERRUPTED. Сохранённый
pendingCall не воспроизводится автоматически: его результат требуется сверить.

## Исполнение и разрешения

Текстовые инженерные запросы проходят через `AgentController → AgentLoop → ToolBroker`.
`/build`, `/repair`, `/edit`, `/workspace push` становятся намерениями этого цикла.
Простые вопросы о списке репозиториев и аккаунте обрабатывает `DirectAnswers` по GitHub
API без передачи данных модели. Составные инженерные поручения не перехватываются
ответом о списке репозиториев.

`ToolCatalog` задаёт host-owned JSON Schema, тип READ/WRITE, разрешение, чувствительность
и необходимость проекта. До исполнения проверяются типы, обязательные и лишние поля,
размеры, числовые ограничения, аккаунт, Project/Task, актуальность контекста и разрешений.
Чувствительные операции требуют одноразового подтверждения точных аргументов.
Запись сериализована между брокерами одного аккаунта/проекта. Повтор одного изменения,
включая сохранённый вызов с неизвестным исходом, блокируется. Сохраняются намерение
вызова и результаты уже выполненной части пакета даже при отмене/исчерпании бюджета.

Произвольных shell, HTTP URL, ключей, управления разрешениями и биллингом в каталоге
нет. Существующие вручную настроенные расширения используют только свои сохранённые
адреса и требуют отдельного подтверждения; смена их конфигурации аннулирует подтверждение.
MCP-схемы с неподдерживаемыми составными условиями отклоняются до исполнения.

Доступ модели к каждому проекту по умолчанию выключен, в том числе после миграции.
Он не включается старым общим переключателем GitHub. Отзыв проверяется перед очередным
запросом/инструментом; смена репозитория снимает согласие. Глобальные настройки чтения
GitHub/файлов сохраняются и дополнительно ограничивают проектный доступ.
Чтение CI-логов по-прежнему требует отдельного согласия; инструменты диагностики этого
этапа возвращают метаданные и категории, а не произвольные журналы.

## Транспорты и бюджет

`NativeToolTransport` кодирует Responses и Chat Completions с сохранением call ID,
assistant function calls и соответствующих tool outputs. Выбор учитывает фактически
настроенный endpoint, модель и протокол. Native включён для известного поддерживаемого
семейства моделей на официальном OpenAI API. Другие endpoint и OAuth/Subscription Proxy,
включая KeyDealer/Nemotron, продолжают использовать существующий провайдерский адаптер
через `EnvelopeTransport`; совместимость OpenAI формата сама по себе не включает native.
Явный HTTP 400/422 об отсутствии поддержки tools допускает переход к envelope.
Ошибки авторизации, квот, сети и сервера не запускают такой повтор.

Бюджет задачи сохраняется до запроса: 12 раундов, после явного разрешения до 25,
до 8 инструментов в ответе и до 100 на задачу. Пакет больше 8 не выполняется частично:
модель получает результаты отказа для всего пакета. Начальный токенный бюджет — 180000;
расширение в Task Screen — 360000. Без usage используются оценки, с usage — не меньше
фактически сообщённого числа токенов. Денежный лимит требует настроенных цен выбранной
модели; без цены денежный расход не выдаётся за известный. Счётчики не сбрасываются
при следующем сообщении или перезапуске.

Контекст компактируется целыми JSON-записями. Данные файлов, HUBBLE.md, память,
описания расширений и результаты инструментов не являются разрешением на действия.
Ответ модели переводит задачу в REVIEW, а не DONE. Независимая проверка Evidence,
RetryPolicy для полного CI-цикла и финальный Work Panel относятся к этапу III.

## Интерфейс и границы этапа

В навигации чата «Проекты» открывает Project Hub. Проект создаётся без Workspace,
может иметь репозиторий и несколько задач. Экран списка задач показывает состояния,
даёт открыть отдельное обсуждение, расширить бюджет и включить/отозвать AI-доступ.
Старые ручные панели Workspace/GitHub пока сохранены; их окончательное объединение и
удаление старых адаптеров выполняются на последующих этапах.

ChangeSet/overlay, изоляция рабочих правок, безопасный ZipballImporter, TaskBranch,
DeltaPublisher и RemoteSync относятся к этапу II. Текущий издатель Workspace сохранён
для совместимости; новый агентский путь блокирует публикацию в main/master.
Не следует считать этот PR завершением требования о публикации исключительно дельты.

## Проверки и приёмка

Обязательная команда:

```sh
./gradlew --no-daemon test assembleDebug assembleRelease lintRelease assembleDebugAndroidTest
```

Новые JVM-наборы: ProjectRegistryMigrationTest, TaskRepositoryTest, AgentControllerTest,
ToolBrokerTest, NativeTransportTest, EnvelopeTransportTest, AgentLoopTest,
OverviewPermissionTest. Реальные Android SharedPreferences/файлы проверяет
`UnifiedAgentUiChecks` из существующих Agent chat UI и RC instrumentation runner.
Используются только фиктивные аккаунты и провайдеры; реальные секреты не нужны.

Перед приёмкой нужны зелёные Android checks, Agent chat UI и Minified Release Xray smoke
на SHA PR. На физическом устройстве остаются обязательными несколько GitHub-аккаунтов,
приватный репозиторий, KeyDealer/Nemotron, SAF и восстановление данных.
Подписанный production APK и установка поверх принятого релиза — этап III.
