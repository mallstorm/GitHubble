# Unified Agent — приёмка и выпуск

Кандидат: `1.0.0-rc4.2.33`, versionCode `80`.
PR: #49 (I) → #50 (II) → #51 (III). Обсуждение отказа от локальной работы не меняет ТЗ.

## Проверка перед выпуском

| Проверка | Способ подтверждения | Статус |
|---|---|---|
| JVM, Debug/Release, lint, Android test compilation | Gradle и отчёты CI текущего commit | Проверяется для каждого изменения |
| RC, Agent UI, Account UI, R8/Xray | Эмулятор Android 13, Actions | Проверяется для каждого изменения |
| Исправление → новый SHA → dispatch → сверка после перезапуска | CiToolsetTest, fake API, без секретов | Автоматизировано |
| Неопределённый dispatch не снимается чужим workflow | CiToolsetTest, fake API | Автоматизировано |
| Старые аккаунты/провайдеры, переписки, файлы и checkpoints | Реальный телефон, пользовательские данные | Требуется приёмка пользователя |
| Изоляция задач, принятие блока diff, откат и восстановление | UI-тесты + сценарий на телефоне | Автоматизированная часть есть; реальная приёмка ожидается |
| Приватный GitHub, несколько аккаунтов, SAF, OAuth/API/KeyDealer/Nemotron | Реальные подключения на телефоне | Требуется приёмка пользователя |
| Подписанный production APK поверх предыдущего Release | Тот же package/certificate, увеличенный versionCode, сохранение данных | После main release workflow |

Не считать тесты с fake API проверкой настоящих GitHub/AI-аккаунтов. Отсутствие сообщения
об ошибке от пользователя не является подтверждением приёмки.

## Порядок объединения

1. Проверить фиксированные HEAD и зелёные проверки #49/#50/#51.
2. Получить явное разрешение владельца на merge и подписанный выпуск (раздел 7 ТЗ).
3. Объединить #49 в main; перенаправить #50 на main и дождаться его актуальных проверок.
4. Объединить #50; перенаправить #51 на main и дождаться его актуальных проверок.
5. Объединить #51 с проверкой ожидаемого HEAD. Не использовать force-push и обход защит.
6. Дождаться существующего main workflow с production-подписью. Проверить точный commit,
   package/version, сертификат, SHA256, Xray, APK и source snapshot опубликованного релиза.
7. Передать ссылку на фактический релиз и провести проверку обновления на устройстве.

Каждый push в main может запустить текущий release workflow: первые два запуска могут
дать промежуточные кандидаты. Итоговым считается только выпуск дерева этапа III с
исправлениями приёмки. Не изменять релизный workflow ради обхода main-only подписи.

## Исправления при подготовке выпуска

- FIX_SOURCE относится к SHA неуспешной сборки, а не к последнему отслеживаемому SHA:
  новый исправленный commit можно отслеживать после dispatch и после перезапуска.
- await_build не снимает DISPATCH_PENDING/UNKNOWN по старому запуску или другому workflow.
  Проверяются workflow ID, SHA, ветка и ID запуска относительно сохранённого priorRunId.
- Регрессионные сценарии сначала воспроизведены на предыдущей реализации, затем исправлены.
