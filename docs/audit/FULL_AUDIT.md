# GitHubble — полный аудит (Проход I)

Дата: 2026-11-11. Основа: `main` @ `2f4c9dc` (RC4.2.31, versionCode 78). Метод: чтение исходников,
сопоставление с предыдущим аудитом (`docs/AUDIT_GITHUBBLE_2026-11-04_RU.md`), анализ вызовов
между классами, CI-прогоны. Живой эмулятор и реальный AI-провайдер в этом проходе **не использовались**;
всё, что не подтверждено тестом или CI, помечено как статическое наблюдение.

## 1. Масштаб

- ~47 000 строк Java/Kotlin в `app/src/main`. `MainActivity.java` — 10 057 строк (≈485 методов): центральный
  «божественный» класс; UI → контроллеры → API проходят через него.
- Агентный слой `agent/` — 49 файлов; GitHub API — `network/GitHubApiClient`, `GitHubSession`; хранилище
  секретов — `security/SecureStore` (Keystore AES-GCM), аккаунты — `auth/GitHubAccountStore`.
- `app/src-compose` не входит ни в один source set (`settings.gradle` включает только `:app`) — мёртвый остаток.
- Тесты: 27 тестовых классов в `agent/`, всего ≈45 в `app/src/test`; CI собирает `test assembleDebug assembleRelease lintRelease`.

## 2. Путь пользовательского действия

`UI → MainActivity (state/ViewModel-роль) → Controller/Service → GitHubApiClient/Storage → Result → UI`.
Для агента: composer → `ProjectRuntime.analyze` (JSON-цикл инструментов, ≤10 раундов, ≤60 вызовов) →
`NativeAgentToolHost` (разрешения, ревью, привязка аккаунта/проекта) → `GitHubAgentOperations` /
`WorkspaceChangeReview` → результат хоста → модель. Карточки файлов рисуются только из метаданных хоста.

## 3. Что устроено хорошо (подтверждено кодом и тестами)

- Явные типизированные инструменты, никакого произвольного URL/метода от модели.
- Уровни разрешений (`AgentPermissionPolicy`), раздельное согласие на раскрытие данных, ревью записей.
- Привязка к аккаунту/диалогу/HEAD, отказ от автоповтора записей после неоднозначной ошибки (`AgentRun` → `unknown`).
- Редактирование секретов в логах (`AgentLogRedactor`, `MemoryPolicy.redactSecrets`), ограничения путей.

## 5. Что отсутствует относительно ТЗ 2.0

Подробно — в `FUNCTION_MATRIX.md`. Главное: нет долговечной задачи, переживающей перезапуск приложения
(журнал `TaskJournal` создан и протестирован, но к чату ещё не подключён); нет Remote Agent Runtime;
нет GitHub App-идентичности для коммитов агента (используется пользовательский токен, автор — пользователь);
нет индекса кода в продакшн-пути; Activity Panel/уведомления агента как отдельный UI не реализованы.
