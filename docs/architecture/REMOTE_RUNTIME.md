# Remote Agent Runtime — анализ и статус

**Статус реализации: НЕ РЕАЛИЗОВАН.** Это документ анализа и проекта (ТЗ §12). Серверного исполнителя, очереди задач и
протокола «клиент ↔ runtime» в коде нет. Ниже — что есть на устройстве сегодня, варианты и рекомендация.

## Что есть сейчас (на устройстве)
- Запуск агента живёт в процессе приложения (`AgentRun`); при закрытии процесса запись о нём остаётся в журнале
  (`AgentRunJournal`, файлы `files/agent-journal`), оборванные запуски помечаются FAILED, кнопка «Продолжить с контекстом» перезапускает
  задачу с протоколом прошлого запуска.
- Результаты GitHub Actions в фоне: прежний `BuildMonitor` (периодический опрос, уведомления) — для репозиториев, которые пользователь
  добавил в наблюдение. Если агент запускает сборку в ненаблюдаемом репозитории, ответ инструмента содержит `background_monitor=false`
  и предупреждение; уведомления при закрытом приложении в этом случае не будет.
- Уведомления агента (`AgentNotifier`) — только пока процесс жив.
Всё это **не** заменяет runtime: цикл модели при закрытии приложения останавливается.

## Варианты (ТЗ §12.2)
| Вариант | Плюсы | Минусы / риски |
|---|---|---|
| Backend-сервис владельца | Настоящая очередь, повторы, хранение журнала, пуш-уведомления | Нужна инфраструктура, учётные данные пользователей и ключи провайдеров на сервере (прямое расширение доверия), эксплуатация |
| Self-hosted runtime у пользователя | Секреты остаются у пользователя | Сложная настройка для мобильного клиента, доступность и NAT |
| Исполнитель на GitHub Actions | Нет своего сервера; логи и артефакты уже в GitHub | Подходит для детерминированных операций (сборка, тесты, релиз), но не для цикла LLM-агента без хранения ключа провайдера в секретах репозитория; лимиты минут и расходы |
| Гибрид: Android + лёгкий backend | Агентный цикл на сервере, устройство — интерфейс и согласования | Лучшее соответствие ТЗ, но наибольший объём работы |

## Рекомендация (не принятое решение)
Двухступенчатый путь: (1) уже сделано — журнал, восстановление, фоновые уведомления сборок; (2) добавить исполнитель на GitHub Actions
для **детерминированных** операций: «собрать и проверить», «собрать релиз» — без LLM, по запросу агента; (3) полноценный
backend-runtime для цикла агента — только после решения владельца о том, где хранятся ключи провайдеров и кто эксплуатирует сервер.
Контракт API для шага (3) описан как проект в `REMOTE_RUNTIME_API.md`.

## Что нужно решить владельцу
1. Допустима ли передача ключей AI-провайдеров и GitHub-токена на сервер (или нужен вариант «агент всегда на устройстве»).
2. Где размещать сервер и кто его поддерживает.
3. Достаточно ли Actions-исполнителя для детерминированных операций на первом этапе.
