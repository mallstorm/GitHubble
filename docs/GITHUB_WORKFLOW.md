# Процесс разработки GitHubble в GitHub

## Назначение веток и Pull Requests

- `main` — интеграционная ветка. Прямые push не используются в обычном процессе.
- `feat/*`, `fix/*`, `chore/*` — рабочие ветки с любым числом промежуточных
  коммитов. Push в них сам по себе не создаёт пользовательских APK.
- Pull Request в `main` показывает diff, историю обсуждения, review и проверку
  **Android checks**. Этот запуск компилирует приложение и выполняет тесты,
  но не загружает артефакты APK/ZIP.
- После принятия PR применяется **Squash and merge**. Один объединённый коммит
  в `main` запускает финальные проверки и публикацию APK, ZIP и архива исходников.
  Отдельный ручной запуск workflow не создаёт релизные артефакты.
- Уведомления GitHubble о пользовательских сборках не поступают от PR-проверок;
  их результаты остаются в списке GitHub Actions для диагностики.
- Автоматический импорт исходников, который раньше сам коммитил прямо в `main`,
  выведен из эксплуатации. Новый импорт исходников оформляется обычным PR.

## Как включить техническую защиту ветки

Владелец открывает **Settings → Rules → Rulesets** (или **Settings → Branches →
Add branch protection rule**), настраивает правило для `main`:
- требовать Pull Request перед объединением;
- требовать успешный статус **Android checks**;
- не разрешать force push и удаление ветки;
- требовать отсутствие нерешённых review-замечаний;
- при появлении независимого reviewer — требовать одно его одобрение;
- разрешить **Squash and merge** для короткой истории `main`.

Не включайте требование одного независимого одобрения, если в репозитории пока
только один участник: GitHub не учитывает собственное одобрение автора PR.
Иначе можно заблокировать доступный штатный путь объединения.

**Текущий статус:** GitHub API сообщил, что rulesets недоступны для этого
приватного репозитория на текущем плане (HTTP 403: требуется GitHub Pro или
публичная видимость); получение настроек branch protection также вернуло 403
«Resource not accessible by integration». Поэтому файл workflow, PR и
договорённость участников **не предотвращают технически** прямой push в
`main`. Пока ограничения доступа не изменены, владелец должен соблюдать
описанный процесс самостоятельно. Нет оснований объявлять защиту включённой.

## Откат и контроль версий

Проверку на эмуляторе следует отличать от приёмки на реальном Android-телефоне.
Не помечайте `main` как стабильную пользовательскую версию автоматически:
после установки владелец фиксирует SHA принятого коммита, соответствующий APK
и, при необходимости, тег `stable/<версия>`. Если новое изменение ухудшило
приложение, новый PR с `git revert <SHA>` безопаснее переписывания истории.
Объединение через PR создаёт один пользовательский итоговый коммит, но проверка
PR и проверка merge в main — это **два отдельных запуска CI**, только один из
которых публикует APK.
