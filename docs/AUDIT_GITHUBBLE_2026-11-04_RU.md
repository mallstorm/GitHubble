# Аудит GitHubble и развитие нативного Git Agent

Дата: 4 ноября 2026. Репозиторий: `mallstorm/GitHubble`.

## Что именно проверялось

Исходная точка аудита — `feature/omnichat-native-agent-phase1`, HEAD
`8a9ce3a71c387542e33facb2461410ce0b554cd6`, открытый draft PR #22.
`main` имеет HEAD `5e5efd911fc819d7dc990833ff66b9cd7a96e32d` и не содержит
всего актуального чата. Поэтому считать состояние `main` состоянием последней
разработки было бы ошибкой. Старые PR #15–20 пересекаются по изменениям и имеют
конфликты с нынешним main; независимо сливать их нельзя.

Для сопоставления получены текущие исходники `Digger401/OmniChat`:
`OmniChatRoot.kt`, `AgentEngine.kt`, `AgentAutoApprovalSetting.kt`, дерево проекта.
Визуал файловых операций сопоставлен с реальным `[[agent-op:...]]` renderer
OmniChat, а не восстановлен по памяти. Использована существующая Android Views
архитектура GitHubble; полной миграции приложения на Compose не делалось.

Ниже «есть» означает наличие связанной реализации в исходниках. Это **не**
утверждение о проверке каждого сетевого сценария с реальным пользовательским
токеном. Отдельно различаются статический анализ, автоматические тесты,
эмулятор и ещё необходимая проверка настоящей авторизации.

## Главный вывод

GitHubble уже является большим рабочим GitHub-клиентом, но исходный Git Agent
не был полноценным единым агентом: модель читала данные через ограниченный
broker, а создание/редактирование/публикация запускались другими ветвями UI.
Наличие соответствующих кнопок не обеспечивало доступ модели к операциям.
Поэтому одной косметической замены оболочки недостаточно.

Новая реализация объединяет рассуждение, чтение и разрешённые изменения
проектов в одном модельном цикле. Пользователь выбирает модель, разрешения и
при необходимости планирование; отдельный выключаемый «обычный чат» больше
не определяет доступность агента. На обычный вопрос модель может ответить без
единого инструмента.

## Карта функций приложения

Обозначения: **есть** — реализовано в коде; **ограничено** — работает только
в указанном объёме; **исправлено** — изменение этого прохода;
**нет** — пользовательская функция отсутствует. Любая запись в GitHub
дополнительно зависит от прав активного токена и правил репозитория.

## Чат: до и после этого прохода

| Требование | Исходное состояние | Новая реализация |
|---|---|---|
| Агент по умолчанию | `ai_chat_agent_mode` по умолчанию false | `agentSend` работает как агент; отдельного выключения в composer нет. |
| Обычные рассуждения без действий | Отдельный обычный режим | Ответ без tool calls в том же агентном режиме. |
| Планирование | Состояние Workspace PLANNING не было полноценным режимом чата | Кнопка «План», состояние по аккаунту и диалогу; host не предоставляет write tools. |
| Переключение после планирования | Несвязанные UI-сценарии | Выключить «План» и продолжить тем же чатом/проектом/моделью. |
| Уровни разрешений | Раздельные consent toggles, без полноценной execution policy | Read only / Review / Local auto / GitHub auto; раскрытие данных и GitHub OAuth независимы. |
| Модель создаёт проект | Эвристика по словам могла менять Workspace во время обсуждения | Модель вызывает `create_workspace`, host проверяет policy и при необходимости спрашивает review. |
| Модель пишет файлы | Отдельная regex/кнопочная генерация | `write_files` в общем runtime, проверка путей, checkpoint, immutable review и stale-file check. |
| Модель создаёт репозиторий | Regex перехватывал ограниченные русские фразы | `create_repository` как исполняемый инструмент; фактический результат возвращается модели. |
| Привязка и импорт | Native команды/меню | Дополнительно `attach_repository` / `import_repository` в model broker. |
| Работа с аккаунтом | Список репозиториев и простая identity | Profile, usage, rate limit, capabilities; подтверждённые editable profile/settings. |
| Работа с Issues/PR/ветками | Преимущественно UI | Чтение + выбранные записи доступны модели, merge закреплён за SHA. |
| Публикация | Native `/workspace push` | Дополнительно `publish_workspace` в том же модельном цикле. |
| Визуал файлов | Текст «применено N файлов» | Host-authored structured operations: папка, карандаш, filename, зелёное `+N`, красное `−N`. |
| Достоверность файловых карточек | Не было отдельного типа события | Карточки рендерятся только из system metadata; обычный текст модели не считается доказательством записи. |
| История файловых событий | Не было | Сохраняются и в fast transcript, и в SQLite archive, additive schema migration 1→2. |
| Общая оболочка | Чат принудительно задавал серую/белую палитру OmniChat | Chat/composer/sheets получают текущие BG/CARD/TEXT/MUTED/GREEN/BORDER GitHubble, включая бежевую тему. |
| Контекст чтения API | Сообщение молча обрезалось на 20 000 символов | Убрана тихая обрезка, увеличен bounded budget, слишком большой запрос даёт явную ошибку. Дублирование project context убрано из runtime callback. |

| Уровень | Чтение | Локальные изменения | Обычные записи GitHub | Профиль/настройки/merge/workflow |
|---|---|---|---|---|
| Только чтение | По отдельным data-consent настройкам | Запрещены | Запрещены | Запрещены |
| Подтверждать изменения, default | По отдельным настройкам | Review | Review | Review |
| Автоматически локально | По отдельным настройкам | Автоматически с checkpoint | Review | Review |
| Автоматически локально и GitHub | По отдельным настройкам | Автоматически с checkpoint | Автоматически | Отдельный review |
| «План» поверх любого уровня | Разрешённое чтение | Запрещены | Запрещены | Запрещены |

Уровни задаются отдельно для каждого GitHub/guest профиля. «План» хранится
отдельно для каждого диалога. Старое выключенное `agent_mode` не отключает
новый broker. Доступ AI к исходникам и метаданным GitHub по умолчанию остаётся
выключенным до решения пользователя. Наличие execution permission не даёт
модели права читать закрытые данные без отдельного consent.

При изменении аккаунта/диалога, отмене запроса, отзыве доступа или включении
планирования выполняются проверки актуальности контекста. Модель не получает
OAuth-токен GitHub. Отклонение операции блокирует дальнейшие записи того же
прохода. Обновление ветки не использует force push.

Автоуровни относятся к новому model broker. Ручные старые команды/кнопки могут
сохранять дополнительные собственные подтверждения; это не означает, что
они автоматически стали фоновыми автономными сценариями.

## Подсчёт строк

`FileChangeStats` сравнивает старый и новый текст по строкам с LCS после удаления
общего префикса/суффикса. Новые файлы показывают `+N −0`, изменение — реальные
добавления/удаления, неизменённые — `+0 −0`. Разные CRLF/LF не считаются заменой
каждой строки. У очень больших несхожих текстов вычисление ограничено; coarse
replacement явно отмечается `≈`, чтобы не выдавать его за минимальный diff.

Статистика относится к выполненной локальной операции, а не обязательно к
накопленному diff всего репозитория относительно GitHub HEAD. Перед публикацией
показывается отдельный план snapshot. Это различие нужно сохранять в UX.

## Что ещё не закончено

1. Нет полноценного долговечного task journal с восстановлением агентной задачи
   после убийства процесса Android. Диалоги/проекты сохраняются, выполняющаяся
   Java Future — нет. Нужен отдельный persistent execution state machine.
2. Нет изолированного shell/test runner, локального Android SDK/NDK и полного
   автономного build environment внутри GitHubble. Сборки сейчас — GitHub Actions.
3. Импорт/публикация — до 180 текстовых файлов и 8 MiB, без полного Git clone,
   бинарных ресурсов/LFS/submodules и автоматического разрешения конфликтов.
   AI-файловый batch ограничен 12 файлами, 80 KiB на файл, 240 KiB суммарно.
4. Нет единого полного набора всех GitHub API tools: reviews, Discussions,
   организации, stars/follows, tags/releases и управление доступами ещё имеют
   UI-операции или отдельные контроллеры вместо общего agent catalog.
5. Нет сквозного streaming текста и состояния каждого tool call по мере SSE
   получения. Сейчас есть busy/cancel и последовательные host events.
6. История сохраняется, но контекст модели ограничен. Это не «бесконечная память»:
   используются recent turns, memory retrieval, обрезанные read results и budgets.
7. Общие Android Views сохраняют дизайн-паттерны OmniChat, но pixel-perfect
   идентичность Compose-оригиналу и полный перенос Live/vision/media не заявляются.
8. Полная capability negotiation с реальными GitHub permissions ещё не является
   транзакционным предварительным dry-run для каждого инструмента. Ошибки 403/404
   нужно показывать с действительным требуемым доступом, не обещая его выдать моделью.
9. Нужны более подробные per-file diff previews до подтверждения записи, открытие
   файла из карточки операции и накопленный change set относительно checkpoint/HEAD.
10. После потери ответа на неидемпотентный remote POST может быть неоднозначный
    результат. Новый broker не ставит такие записи в автоматическую offline replay
    очередь, но ещё нужен durable operation journal/reconciliation перед повтором.

## Приоритетные дефекты вне чата

| Приоритет | Находка | Что требуется |
|---|---|---|
| P1 | Privacy wipe/export не охватывают все новые AI stores/SQLite | Инвентаризация всех хранилищ, единый registry очистки, тест удаления/экспорта без чтения секретов. |
| P1 | Offline mutation queue может повторить неидемпотентный POST после неоднозначного сетевого исхода | Разделить replay-safe PATCH/PUT и создание сущностей; reconciliation/operation IDs. |
| P1 | UI reset HEAD использует non-force переход к предку | Предлагать revert; не заменять незаметно на force push. |
| P2 | MainActivity около 10 тысяч строк и несколько поколений AI-клиентов | Последовательно вынести conversation/session coordinator, tool broker, controllers и миграции. |
| P2 | Catalog metadata шире реально поддержанных подключений | Вычислять availability из транспорта/auth/catalog, убрать общее устаревшее «всё подключим позже». |
| P2 | Документация PR и разные roadmap описывают разные состояния | Единственная текущая capability matrix, ссылки на проверенный SHA/build. |
| P2 | Некоторые инфраструктурные классы перенесены без полного UI/model wiring | Различать imported / compiled / exposed / device-verified. |

## Проверки и границы доказательства

Добавлены unit-тесты execution policy, line diff, host tool dispatch,
запрета неразрешённой записи, обычного рассуждения без tool execution и
сохранности контекста после прежнего порога 20 000 символов.

Android regression дополнен реальными `create_workspace`/`write_files` через
native host без внешних credentials, проверкой фактического содержимого,
`+2 −1`, режима plan/read-only, сохранения operations при переносе в SQLite
и screenshot карточек `file.js +130 −80` / `new.js +160 −0`.

CI выполняет unit tests, Debug/Release compilation, ARM64 checks,
компиляцию instrumentation и Android 13 UI/state suite. Фактический итог
привязан к Actions run проверенного HEAD. Успешный guest-mode эмулятор не
доказывает реальный вход в Cline/Grok/OpenAI/Gemini/Claude и GitHub mutation
с вашим пользовательским токеном.

## Проверка на телефоне после установки

1. Подключить GitHub и нужную AI-модель. В настройках разрешить AI чтение
   GitHub и, если нужны исходники, файлов Workspace.
2. Включить «План». Обсудить архитектуру, попросить сравнить варианты и проверить,
   что запрос «создай репозиторий» не меняет GitHub в этом режиме.
3. Выключить «План». На уровне review попросить создать приватный тестовый repo;
   проверить имя/приватность, подтвердить и сверить результат с GitHub.
4. Создать локальный проект, написать файл, затем изменить его; проверить
   содержимое, checkpoint, строки `+/-`, сохранение истории после перезапуска.
5. Привязать/импортировать тестовый repo, создать ветку, опубликовать текстовый
   проект, создать draft PR. Проверить, что чужой продвинувшийся HEAD блокирует
   устаревшую публикацию, а sensitive operation требует review.
6. Во время запроса отменить его/сменить диалог/включить планирование; проверить,
   что новая запись не начинается после отзыва разрешения.
