# GitHubble: стабильный процесс сборки APK

Эта схема фиксирована. Не меняйте триггеры и условия публикации без отдельной задачи пользователя.

## Pull Request → тестовый APK

Каждый PR в `main` запускает **быстрый цикл RC3.9-типа**: `gradle test assembleDebug assembleRelease` без Android-эмулятора. Это не означает, что весь интерфейс или авторизация проверены автоматически. Расширенные проверки Lint и эмулятора запускаются отдельно вручную через Actions → `GitHubble Android checks and release` → Run workflow → `full_validation=true`. Только после успешной проверки публикуется отдельный Actions-артефакт с установочным **Debug APK**, точным исходным ZIP проверенного HEAD, SHA256SUMS, SOURCE_SHA256, SOURCE_COMMIT и SIGNING_INFO. Артефакт помечен `githubble-pr<NUMBER>-...`, хранится 14 дней. Release keystore и прочие signing secrets не используются для PR.

При неудачном тесте артефакт APK не публикуется: ошибку исправляют в исходной ветке PR. Никакой необходимости сливать PR только ради получения APK нет.

## main → финальная сборка

После принятия PR merge в `main` автоматически запускает тот же CI и публикует Actions-артефакт `githubble-<VERSION>-<SHA>` с Debug APK, unsigned Release APK, точным ZIP дерева main, SHA256 и метаданными подписи. Хранение Actions-артефакта — 30 дней. Если настроен постоянный release keystore в GitHub Actions Secrets, дополнительно собирается подписанный Release APK; unsigned Release устанавливаемым не является.

Только после **успешного** завершения быстрых unit-тестов и компиляции в `main` отдельное задание `publish-release` получает её артефакт, сверяет SHA256 и `SOURCE_COMMIT`, затем создаёт приватный GitHub **prerelease** с тегом `build-<VERSION>-<SHORT_SHA>`. Публикуются Debug APK, исходный ZIP, контрольные суммы и информация о подписи; подписанный Release APK публикуется только при наличии настоящей release-подписи. Неподписанный Release APK в Releases не выкладывается. Тег с SHA позволяет не перезаписывать предыдущие версии при повторном использовании VERSION_NAME. При повторном запуске этого же коммита файлы релиза обновляются, вместо создания дубликата.

Для `publish-release` задано только требуемое `contents: write`; у задания `build`, в том числе на PR, остаётся `contents: read`. Секреты подписи не передаются заданию публикации. Выполнение `workflow_dispatch` не создаёт Release: публикация происходит только после `push` в `main`.

## Как откатить этот режим

Если быстрый путь приводит к регрессиям, верните обязательный Lint и эмулятор через отдельный PR: отмените коммит изменения CI (или восстановите `.github/workflows/android.yml` из коммита `a2b05167c51eb482aa4e2f7d84f97e21a4cccaa1`), не откатывая исходники Android, Release-публикацию или историю `main`. Ручной расширенный тест не публикует релиз, поскольку публикация разрешена только для `push` в `main`.

## Доставка пользователю

Итоговый APK и исходники доступны как отдельные файлы в GitHub Releases, без распаковки Actions ZIP; приватный репозиторий требует авторизованного GitHub-доступа. Для приложения APK непосредственно в чат необходимо отдельно получить бинарный файл, проверить SHA256 и предоставить реально доступный файл: одна ссылка на приватный Release **не** является общедоступной прямой ссылкой на APK. PR-тестовый APK остаётся только в Actions на 14 дней. Указывать commit SHA и различать тестовый Debug от production-signed Release.

Debug APK предназначен для проверки, его ключ подписи в разных запусках CI может отличаться; обновление поверх установленной другой сборки без удаления приложения может быть невозможно. Production-публикацию отдельно включать только после настройки **постоянного** keystore и проверки сертификата. Не удалять установленное приложение ради обновления без предупреждения о потере локальных данных.

## Ограничения

GitHub Actions не подменяет ручные UI-проверки на реальном Android-устройстве. Обычные ветки вне PR и main не публикуют installable APK.
