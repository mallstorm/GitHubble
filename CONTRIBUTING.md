# Как вносить изменения в GitHubble

Основная ветка `main` предназначена для объединённых изменений. Работайте в отдельной ветке
`feat/<название>`, `fix/<название>` или `chore/<название>`, созданной от актуальной
`main`. Не отправляйте изменения напрямую в `main`.

## Обычный цикл разработки

1. Создать ветку от `main`. Вносить связанные правки и локально проверять результат.
   Промежуточные коммиты остаются в рабочей ветке, без пользовательских APK.
2. Открыть Pull Request в `main` с понятным описанием, рисками, тестами и
   скриншотами, если менялся интерфейс. Использовать шаблон PR.
3. Дождаться успешного **Android checks**: компиляция, unit tests, lint,
   Android-инструментальные тесты на эмуляторе. После успешных проверок PR публикует тестовый Debug APK и ZIP проверенных исходников в Actions на 14 дней; подписанный production Release на PR не создаётся.
4. Владелец изучает Files changed, комментарии и тесты. Если есть второй разработчик,
   попросить его выполнить отдельный review. Автор PR не может засчитать собственное
   одобрение за независимое review.
5. После согласования объединить **Squash and merge**: несколько рабочих коммитов
   превращаются в один итоговый коммит в `main`. Удалить рабочую ветку.
6. Push в `main` запускает итоговую проверку и, только после её успеха,
   публикует APK/ZIP/исходники в Actions и отдельный GitHub prerelease с Debug APK и точным ZIP исходников. GitHub Releases приватного репозитория требуют авторизации для скачивания. Проверить Debug APK на реальном устройстве;
   только после приёмки отмечать версию как проверенную.

Исправляйте замечания дополнительными коммитами **в том же PR**, не открывайте отдельный
PR на каждую правку. При ошибке в `main` сделайте `git revert` через новый PR.
Не переписывайте и не force-push историю `main`. Предыдущие сборки и принятые
версии храните отдельно от промежуточных проверок.

## Безопасность

Не добавляйте OAuth-токены, секреты GitHub Actions, приватные ключи, пользовательские
дампы, пароли и доступы в коммиты и артефакты. Запрещено выдавать положительное
завершение задачи без успешного CI и проверки результата на устройстве, если
изменение затрагивает UI/авторизацию/интеграцию с реальным аккаунтом.

## Защита main

Политика выше соблюдается командой добровольно, пока GitHub не разрешает настроить
branch protection для приватного репозитория. Чтобы сделать её технически обязательной,
см. [описание ограничений и настройку правил](docs/GITHUB_WORKFLOW.md).
